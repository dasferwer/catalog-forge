# Как объяснить CatalogForge на интервью

**Задача:** загрузить большой каталог, проверить строки, обработать дубли и
пережить падение процесса без повторного счёта данных и частичной публикации.

**Путь данных:** HTTP stream + SHA-256 → неизменяемый файл → job/lease →
потоковый parser → bounded batch → PostgreSQL COPY → staging/checkpoint →
атомарный UPSERT опубликованного каталога.

**Главное решение:** checkpoint коммитится вместе с данными пакета. Сохранить
номер строки отдельно от записи товаров недостаточно: сбой между этими
действиями приводит к пропуску или повторной обработке. Token защищает от
старого worker после восстановления другим процессом.

**Дубликаты:** последняя валидная строка SKU побеждает. Сначала убираются
дубли внутри пакета, затем сравнивается номер строки с сохранённым staging.
При повторном импорте fingerprint позволяет выделить неизменённые записи.

**Почему есть staging:** читатели каталога получают полностью применённую
версию импорта. За это нужно платить дисковым пространством и стоимостью
одной финальной транзакции. Удаления SKU, отсутствующих в файле, нет.

**Что показать:** миллион товаров, SIGKILL после checkpoint, прежний каталог
во время загрузки, продолжение с сохранённой строки, точные счётчики и peak RSS.
Затем показать восстановление CSV с многострочным полем и JSON-массива.

**Что честно назвать ограничениями:** JSON-массив перечитывает префикс при
resume; запись ограничена 128 KiB, а размер пакета влияет на память; лимит RSS относится к benchmark
worker; источник хранится в локальном volume; автоматического GC нет.

Корректная формулировка опыта: «Разработал портфолио-сервис импорта каталогов
с COPY, checkpoint, дедупликацией и атомарным применением; проверил сценарий
миллиона строк с аварийным завершением worker».
