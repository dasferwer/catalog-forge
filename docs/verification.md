## HTTP-сценарий

Через API загружены CSV, JSONL и JSON-массив. CSV содержит 10 000 товаров,
одну повторную валидную запись и одну невалидную. Проверены точные счётчики,
последняя валидная версия SKU, повторный импорт без изменений и validate_only.
Время CSV-сценария — 2.41 с, peak RSS worker — 63.41 МиБ.

## Миллион строк и аварийное восстановление

Команда: `uv run python scripts/recovery_smoke.py --rows 1000000`.

- Вход: **1 000 002** строки данных: миллион уникальных SKU, один дубль,
  одна невалидная строка.
- Worker принудительно завершён через SIGKILL после зафиксированной позиции
  **4000**.
- До применения импорта API показывал **0** товаров нового каталога.
- После запуска worker восстановился **с той же контрольной точки**.
- Итог: **1 000 000** товаров, один дубль, одна ошибка, одно восстановление.
- Время сценария: **49.9 с**, включая остановку и ожидание lease.
- Пиковый RSS worker: **63.61 МиБ** при пакете 2000 записей.

Это измерение Python worker. Память PostgreSQL, WAL, staging на диске,
Docker Desktop и клиент загрузки сюда не входят. JSON-массив может требовать
память для большого отдельного объекта; benchmark использует обычные CSV-строки.

## Что проверяют тесты

- Checkpoint и staging откатываются вместе при ошибке после COPY.
- Ошибка перед событием успеха откатывает весь финальный merge.
- Устаревший token не может записать пакет или применить импорт.
- Пауза и resume, отмена без частичной публикации, skip/reject, validate_only.
- Продолжение CSV, JSONL и JSON-массива, включая Unicode и многострочный CSV.
- Повторные ключи, конкурентная загрузка, лимит размера и SHA-256.
- Невалидные числа, точность денег, ограниченная выборка ошибок при полном счёте.
- Проверка владельца, дедупликация, неизменённые/изменённые товары.
- Удаление завершённого импорта сохраняет опубликованные товары.
