# Архитектура CatalogForge

## Данные

`catalogs` и `products` представляют опубликованный каталог. `import_jobs`
содержит формат, настройки, неизменяемый исходник, статус, lease/token,
контрольную точку и счётчики. `staged_products` хранит последнюю валидную строку
каждого SKU. `row_errors` хранит ограниченную выборку ошибок.

Сохранённая позиция описывает полностью зафиксированный префикс файла:
`processed_rows = valid_rows + invalid_rows`. Для завершённого импорта
`duplicate_rows = valid_rows - count(staged_products)`.

## Загрузка

Запрос создания защищён advisory lock и уникальным ключом пользователя.
Повтор того же ключа возвращает тот же job; изменение параметров — 409.
API резервирует upload lease, пишет поток в уникальный `.part`, проверяет SHA-256,
делает fsync/rename и только затем переводит job в ready. В БД записывается
сгенерированный путь; клиент не может передать путь к локальному файлу.

Проверка SHA-256 повторяется при запуске и восстановлении worker. Файл
неизменяем после загрузки. Если ответ загрузки потерян, клиент сначала читает
статус job. После оборванной загрузки файл можно повторить по истечении upload
lease. Отдельные временные файлы не считаются готовыми исходниками.

## Пакет и контрольная точка

1. Worker захватывает ready job или running job с истёкшей арендой через
   `FOR UPDATE SKIP LOCKED` и записывает новое поколение token.
2. Потоковый парсер выдаёт ограниченный пакет строк.
3. В транзакции worker блокирует job, проверяет token, статус и управляющие флаги.
4. Нормализованные строки поступают через binary COPY во временную таблицу.
5. `DISTINCT ON` оставляет последнюю строку SKU в пакете; UPSERT в staging
   сохраняет строку с наибольшим номером среди всех пакетов.
6. Ошибки, счётчики и checkpoint коммитятся вместе со staging.

Ошибка до commit откатывает весь пакет. Ошибка после commit восстанавливается
из сохранённого checkpoint. Устаревший worker не может записать следующий
пакет или применить импорт после смены token.

CSV использует границу логической записи, включая quoted multiline. JSONL
использует конец строки. ijson для JSON-массива повторно пропускает уже
зафиксированные элементы; позиция байтов внутри буфера парсера не используется
как checkpoint. Это сохраняет корректность независимо от его read-ahead.

## Атомарное применение

После полного чтения worker снова блокирует job, затем каталог. Политика
`reject` прекращает применение при ошибках. `validate_only` сохраняет только
staging и отчёт. Обычный режим рассчитывает created/updated/unchanged и делает
UPSERT товаров в той же транзакции, что и конечный статус job и событие успеха.
Fingerprint нормализованного содержимого предотвращает лишние UPDATE.

Мутации опубликованного каталога доступны только через этот путь. Два импорта
одного каталога сериализуются на его строке. До commit читатели видят прежнее
состояние; после commit — новое. Отмена проверяется на границе пакета и перед
применением. Уже коммитящаяся транзакция не прерывается задним числом.

## Хранение и ограничения

- Исходники лежат на persistent volume. API пишет, worker монтирует его read-only.
- Запросы и отчёты проверяют владельца job/catalog; у пользователя нет доступа
  к файловым путям или внутреннему lease token.
- CSV/JSONL ограничивают физическую строку 128 KiB, CSV — также логическую запись.
- JSON-массив требует память для одного элемента; большой отдельный объект
  может потреблять больше памяти, чем обычная товарная запись.
- Объём памяти не растёт пропорционально числу обычных записей, но staging,
  индексы, WAL и опубликованные товары занимают место в PostgreSQL.
- Порог RSS в benchmark проверяет Python worker, а не суммарную память БД,
  Docker Desktop или клиента. Он не является универсальным лимитом всех входов.
- Удаление терминального job удаляет staging и отчёты через FK CASCADE,
  затем пытается удалить исходный файл. При ошибке файловой системы API
  возвращает `source_file_removed=false`; товары каталога сохраняются.
- Политика автоматического удаления старых исходников/осиротевших `.part`
  не реализована. Для длительной эксплуатации нужна отдельная retention/GC-задача.
